# Phase 2 implementation decisions

> Historical record: the local backend foundation was first planned around the Expo client. Decision [0004](0004-pwa-pivot.md) supersedes its mobile session, offline-storage, and deployment choices; retain its domain/schema foundations only where they fit the PWA.

**Status:** Local foundation implemented; deployment and device verification remain open. No Neon project or provider credentials were supplied or provisioned.

## Decisions

| Area | Decision |
| --- | --- |
| API runtime | A Hono TypeScript modular monolith. API routes call domain services; database and future AI providers stay behind separate modules. |
| Identity | Self-host Better Auth on the Hono API with email/password sessions. New accounts require a one-time invitation tied to an email. Better Auth session renewal stays server-controlled; the Expo client stores its session cookies in SecureStore. Email verification and password recovery wait until an email delivery provider is chosen. |
| Database | Neon Postgres via `pg` and Drizzle. Better Auth owns its auth schema migration; Drizzle owns app tables. `npm run db:migrate` runs the auth migration first and the app migration second. Use the Neon pooled Node.js connection URL in `DATABASE_URL`. |
| Account isolation | Per-user profile, sync, and upload tables have a `user_id`, an auth-user foreign key, and forced PostgreSQL row-level security. User requests set the account ID within the same transaction and also filter by that ID in the query. The internal job queue has a worker-only policy enabled inside authenticated worker transactions. Global food catalog rows are readable independently of account. |
| Offline sync | The API accepts typed, versioned changes with a user-scoped idempotency key. It records a per-user pull cursor and tombstones. Base-version mismatches return a conflict instead of overwriting a newer server value. Food-log nutrition is calculated from the catalog in the API and stored as a snapshot. |
| Device database | Expo SQLite uses SQLCipher. A random database key is stored in SecureStore. Local records, cursors, and outbox entries are scoped to the signed-in account. Switching accounts waits for pending changes to sync, then clears the previous account's local cache. |
| Invitations | A local CLI creates random, email-bound invitation codes and stores only a SHA-256 digest. The signup handler reserves a code during registration and redeems it after a successful response. Share the printed code privately. |
| Private uploads | The database includes owner-scoped upload metadata and the API checks ownership. Actual upload/download signing is unavailable until a private object-storage provider and credentials are selected; the endpoint returns a controlled unavailable response. Food-photo recognition remains a later phase. |
| Durable jobs | The schema includes a job queue with idempotency, leases, retry delay, and expiry recovery. Internal claim/complete/fail routes require `JOB_DISPATCH_SECRET`. A scheduled worker and deployment target remain unconfigured until the Neon account/runtime is available. |
| AI configuration | `OPENROUTER_API_KEY` and `AI_MODEL=minimax/minimax-m3` are server-only settings for later AI phases. No model requests are made by the Phase 2 API. |

## Configuration

The root `.env.example` lists backend values and later server integration placeholders. For local API use, fill `DATABASE_URL`, `AUTH_SECRET`, and `AUTH_BASE_URL` in the ignored root `.env`. Set `EXPO_PUBLIC_API_BASE_URL` in `apps/mobile/.env`; it is public app configuration. See [environment setup](../ENVIRONMENT.md).

Drizzle tracks row-level policies, checks, and `ENABLE ROW LEVEL SECURITY`. PostgreSQL `FORCE ROW LEVEL SECURITY` is kept in the generated SQL migrations and must remain present when editing these migrations.

## Verification still required

- Supply a Neon development URL and run `npm run db:migrate` against that account.
- Start the API with real auth settings and create two invited accounts.
- Verify cross-account reads and writes are denied by PostgreSQL RLS, repeated sync requests apply once, and stale versions return conflicts.
- Build the Android development APK to verify SQLCipher and SecureStore on the owner's phone.
- Choose and configure private object storage before enabling uploads.
- Choose and deploy the worker scheduler before enabling asynchronous planning runs.

Until these checks pass, Phase 2 is not complete. Basic screens continue to use their Phase 1 demo data.
