# Phase 0 decision log

**Status:** Desk research and implementation decisions recorded on 20 October 2026. Android-phone checks and cloud-account checks remain open; those are called out below and do not block manual tracking or the Phase 1 UI shell.

## Product contract for the first usable version

- Android-first, private APK for the owner and invited friends. The public GitHub repository contains source only; no credentials, health records, or private food photos.
- Adult, general-wellness tracking. The app records user-entered measurements and offers reviewed plans. It does not diagnose, prescribe treatment, or claim that a calorie estimate predicts a person's weight change.
- The first usable path is manual food, activity, and weight entry, plus the goal-versus-measured-progress screen. Network-dependent services must not make those basic screens unusable.
- Keep the agreed white, black, gray, and lime/green interface. Give the actual measured trend and accepted goal path the most prominent graph treatment.
- Keep MiniMax M3 (`minimax/minimax-m3`) behind a server-side OpenRouter adapter. Food-image identification is its own candidate-producing call; the user confirms the dish and portion before nutrition is logged. Meal and workout generation stay as two separate, bounded LangGraph workflows.
- No cloud resources or provider credentials were created as part of this phase.

## Architecture decisions

| Area | Decision for implementation | Proof still required |
| --- | --- | --- |
| Android client | Expo + React Native + TypeScript + Expo Router. Begin with the current Expo Go-compatible SDK template for rapid screen iteration; use a custom development build for native integrations. Keep the native minimum version provisional until the friends' device list is known. | Verify the pinned template and all native packages with a clean install and an Android build. |
| App navigation | Four primary destinations: Home, Food, Activity, Progress. Use Router stack behavior so Android Back returns from details to the originating tab. | Try on the owner's phone with larger system text. |
| Main graph | Start with an app-owned line-chart component using `react-native-svg`. It will separately encode the accepted target path, measured daily points, and measured trend; missing measurements remain gaps. This avoids pulling Skia/Reanimated into the first shell. Keep its data contract independent so a future chart package can replace the renderer. | Validate touch, label readability, and rendering on a real phone before marking Phase 1 complete. |
| On-device persistence | `expo-sqlite` for records/outbox later; `expo-secure-store` for auth credentials. Never store a session secret in ordinary preferences or an `EXPO_PUBLIC_*` value. | Add both packages only in the phase that implements local persistence/auth and test a signed build. |
| Backend | Keep one TypeScript modular monolith with an authenticated Hono HTTP API and domain modules. Keep provider calls behind adapters. Neon Postgres remains the source of truth. | Verify Neon Functions HTTP behavior, supported resource limits, and same-region connectivity in the owner's Neon account before choosing its deployment target. A small Node host remains the fallback. |
| Durable planning work | Create the AI run and job record in one database transaction, return `202` only after commit, then process with a leased worker and persisted status/checkpoints. Neon Function Triggers can run scheduled dispatch/recovery as of the current docs; a trigger is a scheduler, while the Postgres job row and lease remain the durable queue. Use an external authenticated dispatcher if the account/plan cannot run the required cadence. | Provision a development branch and verify invocation cadence, retry behavior, timeout, and secret injection before Phase 2/8. |
| Identity | Evaluate Neon Auth with a React Native/Expo-compatible Better Auth client and SecureStore-backed session storage. Keep the API identity adapter replaceable. | Prove sign-in, token refresh, sign-out, and API bearer-token validation on Android before adopting it. If native refresh/storage is not supported by the actual SDK route, select a managed auth provider that is. |
| Images | Keep originals private, upload through short-lived authorization, pass only an approved image to the backend vision adapter, and delete temporary originals according to the retention policy. | Verify Neon Object Storage private access, signed requests, and lifecycle behavior for the account. Do not assume these from the presence of Postgres. |
| Model routing | OpenRouter M3; validate JSON against Zod/domain rules on the server. Require a serving endpoint that supports the actual parameters. Never expose an OpenRouter key in the APK. | The model has image and structured-output capabilities, but endpoint capabilities vary. Test the combined image + schema request and usage metadata against the selected route before enabling it. |
| Health data | Health Connect is optional. Manual step/workout entry is the fallback and remains usable if the provider, permission, or phone lacks data. Do not add imported steps to a second manually recorded copy of the same session. | Install a custom build and test availability/permission/revocation and repeated imports on the owner's Android phone. |
| Calendar | Local notifications are the initial reminder path. Google Calendar is an optional, later integration with explicit account consent and deterministic event IDs. | Test the native authorization flow and production consent requirements when Phase 11 begins. |
| Database region | Choose the nearest region shared by the owner and likely friends that also supports the selected Neon Auth, Functions, and storage features. | Decide after seeing account region options; do not provision without user-side access. |

## Confirmed provider facts and limits

- Expo SDK 58 is in a transition period in the current Expo documentation; the documented unqualified template remains SDK 57 for Expo Go compatibility. The app will use a pinned template and lockfile rather than the moving `latest` tag. [Expo Router introduction](https://docs.expo.dev/router/introduction/)
- Expo Notifications documents local scheduling and requires a development build for Android remote push; the initial feature is local reminders, so push credentials are not a Phase 1 dependency. [Expo Notifications](https://docs.expo.dev/versions/latest/sdk/notifications/)
- Neon documents JavaScript/TypeScript Functions and scheduled Function Triggers. A scheduled invocation can wake a worker, but our durable queue, idempotency, and lease semantics belong in application tables. [Neon Function Triggers](https://neon.com/blog/your-neon-functions-can-now-run-on-a-schedule)
- The current OpenRouter M3 page lists image input and JSON-schema response formatting, while noting the serving endpoint determines supported parameters. We will schema-validate every response and require an endpoint that accepts the parameters sent. [OpenRouter M3](https://openrouter.ai/minimax/minimax-m3) [OpenRouter structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs)
- Current Health Connect bridge compatibility and permission behavior must be checked against the package actually installed and the owner's device. A desktop cannot prove phone availability or consent behavior.

## Device and account follow-ups

Before Phase 2 deployment, record the owner's Android version/device and the oldest Android version among friends; select the actual native build minimum from that matrix. Before Phase 2, verify Neon Auth, Functions, Object Storage, and region support in the owner's account. Before Phase 7, run the M3 combined image/structured-output request and confirm provider privacy/routing settings. Before Phase 10/11, do Health Connect and Calendar authorization checks on the target phone/account.

Until those checks pass, the safe fallbacks are manual tracking, the Node API/worker adapter, and local reminders. These limitations are represented in Phase 0's status; they are not presented as completed integration tests.
